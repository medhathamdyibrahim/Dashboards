# دفتر الصفقات — CRM + PO & Invoices Tracker

نظام تتبع كامل للسلسلة: **أمر شراء (PO) ← عرض سعر (Quotation) ← أمر بيع (Sales Order) ← شحن (Dispatch) ← فاتورة (Invoice) ← تحصيل (Payments)**، مبني بـ React + TypeScript + Tailwind على الواجهة، و Supabase (قاعدة بيانات + Auth + تخزين ملفات) في الخلفية.

## المميزات
- تسجيل دخول/خروج بـ Supabase Auth. أول مستخدم يسجل في النظام يصبح **Admin** تلقائيًا.
- **صلاحيات ديناميكية**: الـ Admin يتحكم من صفحة "الإعدادات" في كل حاجة يقدر كل Role (مبيعات / مالية) يعملها في كل قسم (عرض / إضافة / تعديل / حذف / موافقة).
- **تتبع كميات تلقائي** في كل مرحلة: مينفعش تخصص لأمر بيع كمية أكبر من الكوتيشن، ولا تشحن أكبر من أمر البيع، ولا تفوتر أكبر من اللي اتشحن — النظام بيمنع ده تلقائيًا (Database Triggers).
- **Workflow موافقات**: عرض السعر محتاج موافقة (مالية/أدمن) قبل ما يتأكد، والفاتورة محتاجة اعتماد قبل ما تتصدر.
- **Multi-currency**: كل مستند (PO / Quotation / SO / Invoice) له عملته الخاصة.
- **دفعات جزئية**: كل فاتورة تقدر تتحصل على أكتر من دفعة، والحالة (غير مدفوعة / جزئي / مدفوعة بالكامل / متأخرة) بتتحدث تلقائي.
- مرفقات (PDF/صور) لكل مستند عبر Supabase Storage.

## خطوات التشغيل

### 1. إنشاء مشروع Supabase
اعمل حساب/مشروع جديد على [supabase.com](https://supabase.com) (الخطة المجانية كافية للبدء).

### 2. تشغيل قاعدة البيانات
افتح **SQL Editor** داخل مشروع Supabase، وانسخ كل محتوى الملف `supabase/schema.sql` وشغّله دفعة واحدة. الملف بينشئ كل الجداول، الصلاحيات، الـ Triggers، والـ Views.

> إذا احتجت تشغيله أكتر من مرة، الملف آمن لإعادة التشغيل (يستخدم `if not exists` / `or replace` قدر الإمكان).

### 3. إنشاء Storage Bucket للمرفقات
من قسم **Storage** في Supabase، أنشئ Bucket اسمه بالظبط `attachments` واختار **Private**. سياسات الوصول (Policies) اتعملت بالفعل داخل `schema.sql`.

### 4. ربط المشروع بمفاتيح Supabase
من **Project Settings > API**، انسخ:
- `Project URL`
- `anon public key`

انسخ ملف `.env.example` باسم `.env` واملأ القيمتين:
```
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=xxxxxxxxxxxxxxxxxxxxx
```

### 5. تثبيت الباكدجات والتشغيل محليًا
```bash
npm install
npm run dev
```
هيفتح على `http://localhost:5173`.

### 6. إنشاء أول حساب (Admin)
افتح التطبيق واعمل "إنشاء حساب" بإيميلك. **أول حساب يتسجل في النظام يصبح Admin تلقائيًا** ويقدر يدخل صفحة "الإعدادات والصلاحيات" علشان يضيف باقي المستخدمين ويحدد صلاحياتهم.

### 7. النشر (Deploy)
المشروع عبارة عن SPA عادي (Vite build)، تقدر تنشره على أي استضافة ثابتة:
```bash
npm run build
```
الناتج هيبقى في مجلد `dist/` — ارفعه على Vercel / Netlify / Cloudflare Pages أو أي استضافة تدعم Static Sites، مع إضافة نفس متغيرات `.env` في إعدادات الاستضافة.

## هيكل قاعدة البيانات (ملخص)
```
purchase_orders (PO)  →  quotations  →  sales_orders  →  dispatches  →  invoices  →  payments
    └─ po_items            └─ quotation_items  └─ so_items   └─ dispatch_items  └─ invoice_items
```
كل مستند رئيسي له جدول "سطور" (items) خاص به يسمح بأكتر من منتج بكميات وأسعار مختلفة. التفاصيل الكاملة والتعليقات موجودة داخل `supabase/schema.sql`.

## بنية المشروع
```
src/
  context/AuthContext.tsx     # الجلسة، البروفايل، والصلاحيات (can/isAdmin)
  components/                 # مكونات مشتركة (Modal, StatusPill, AttachmentsPanel...)
  pages/
    PurchaseOrders/  Quotations/  SalesOrders/  Dispatches/  Invoices/  Payments/
    Customers.tsx  Products.tsx  Settings.tsx  Dashboard.tsx  Login.tsx
supabase/schema.sql            # قاعدة البيانات كاملة (جداول + RLS + Triggers + Views)
```

## ملاحظات مهمة
- الصلاحيات الافتراضية بعد أول تشغيل: **مبيعات** (تحكم كامل في PO/Quotation/SO)، **مالية** (تحكم كامل في Dispatch/Invoice/Payment + موافقة الكوتيشن). تقدر تغيّرها في أي وقت من "الإعدادات".
- كل الحسابات الجديدة بعد أول Admin بتفضل **بدون صلاحية** لحد ما الـ Admin يحدد لها Role من صفحة الإعدادات — ده إجراء أمان مقصود.

## سجل تحديثات: تنفيذ 7 متطلبات تطوير

### 1. إعادة تسمية التبويبات
"PO" أصبح **Opportunities (الفرص)**، و"Quotation" أصبح **Quotations (Confirmed PO's) — عروض الأسعار (أوامر شراء مؤكدة)** في كل مكان بالتطبيق (القوائم، العناوين، الصلاحيات، التصدير). أسماء الجداول في قاعدة البيانات (`purchase_orders`, `quotations`) سابتها زي ما هي عمدًا لتجنب Migration خطر يكسر الـ Foreign Keys — التغيير في واجهة العرض فقط.

### 2. التشفير من جانب العميل (Client-Side Encryption)
- المكتبة: `crypto-js` (AES)، المفتاح في `window.__APP_CONFIG__.ENCRYPTION_KEY` بداخل `index.html` (مفتاح واحد ثابت لكل النظام، حسب الاختيار).
- **مهم غيّر المفتاح الافتراضي في `index.html`/`config.js` لقيمة سرية طويلة قبل النشر الفعلي.**
- الطبقة شفافة بالكامل: `src/lib/secureClient.ts` توفر `secureFrom(table)` كبديل مباشر لـ `supabase.from(table)` — أي بيانات مُرسلة تتشفر تلقائيًا، وأي بيانات راجعة تتفك تلقائيًا.
- **تحديث لاحق (بقرار صريح):** تم توسيع نطاق التشفير ليشمل **الكميات والأسعار والمبالغ** (`quantity`, `unit_price`, `amount`, `printed_qty`, `delivered_qty`) في كل الجداول (po_items, quotation_items, so_items, dispatch_items, invoice_items, payments, production_entries) — راجع القسم "تحديث كبير: تشفير الكميات والأسعار" تحت لتفاصيل الأثر الكامل على المعمارية.
- **الحقول المشفّرة حاليًا** (`src/lib/encryptedFields.ts`): كل الملاحظات، بيانات الاتصال (تليفون، إيميل، عنوان)، الرقم الضريبي، سبب الرفض، مرجع الدفع، اسم الملف المرفق + **كل الكميات والأسعار والمبالغ المالية**.
- **الحقول اللي سابتها بدون تشفير (مش اختياري، قيد تقني):** الـ Primary/Foreign Keys (لأن التشفير غير حتمي — نفس القيمة بتنتج نص مختلف كل مرة، فمينفعش تُستخدم كمفتاح ربط بين الجداول)، والحالات (status) والتواريخ وأسماء العملاء/الفرص (مطلوبة للبحث والفلترة والتقارير على مستوى قاعدة البيانات).

### 3. سجل المراجعة والاستعادة (Audit Trail & Rollback)
- جدول `audit_log` + Trigger عام (`audit_trigger_fn`) مرتبط تلقائيًا بكل الجداول الأساسية (عملاء، منتجات، فرص، عروض أسعار، أوامر بيع، شحنات، فواتير، تحصيلات، إنتاج، مرفقات).
- كل عملية Insert/Update/Delete بتتسجل تلقائيًا مع: المستخدم، التوقيت، القيمة القديمة، القيمة الجديدة.
- صفحة **`/audit`** (أدمن فقط): فلترة بالجدول/الإجراء/التاريخ، عرض الفروقات (Diff)، وزرار **استعادة** يرجّع القيم السابقة (وده بيتسجل هو نفسه كعملية تعديل جديدة — سجل تاريخي كامل بدون "محو" أي حاجة).

### 4. النسخ الاحتياطي (Admin Backup)
- قسم جديد في **الإعدادات** (أدمن فقط): زرار "تصدير نسخة احتياطية كاملة" بيجمع كل جداول النظام (مع فك تشفير الحقول المشفّرة عشان الملف يكون قابل للقراءة) وينزّله كملف JSON واحد على جهاز الأدمن مباشرة (Download).

### 5. اختيار الفرصة الذكي (Smart Opportunity Selection)
- View جديد `v_opportunity_selector` في قاعدة البيانات بيحسب: قيمة الفرصة، قيمة عروض الأسعار المؤكدة (SO/PO Value)، والقيمة المتبقية.
- كومبوننت `SearchableOpportunitySelect` بديل الـ dropdown العادي في فورم "عرض سعر جديد": بحث حي برقم الفرصة/الاسم/العميل، وعرض القيم الثلاث لكل نتيجة.

### 6. التقارير الهرمية الذكية (Smart Hierarchical Reports)
- View جديد `v_hierarchy_report` بيربط: الفرصة → عرض السعر (أمر شراء مؤكد) → أمر البيع → الفاتورة.
- قسم جديد أعلى صفحة **التقارير**: شجرة قابلة للطي/التوسيع، بحث، فلاتر (مدير الحساب، العميل، المنطقة، التاريخ)، وتصدير Excel للبيانات المفلترة حاليًا.

### 7. إعادة الهيكلة والتنظيم (Refactoring)
الكود المصدري (`src/`) منظم بالفعل في ملفات صغيرة (أكبر ملف ~410 سطر) — كل صفحة/مكون في ملفه الخاص. ملف `app.js` الضخم (~1MB) اللي يظهر في نسخة النشر (`crm-app-static.zip`) هو **ناتج بناء نهائي (bundle)** وليس الكود المصدري؛ تم إبقاؤه ملفًا واحدًا (IIFE) بقرار مقصود حتى يعمل التطبيق بفتح `index.html` مباشرة (نقر مزدوج) بدون أي سيرفر — تقسيمه لملفات JS متعددة (ES Modules) كان سيلغي هذه الميزة بسبب قيود CORS على `file://`.

## ⚠️ قبل النشر الفعلي (Production)
1. **شغّل `supabase/schema.sql` كاملاً من جديد** على مشروع Supabase (يحتوي على الإضافات الجديدة: `audit_log`, وViews محدّثة). آمن لإعادة التشغيل.
2. **غيّر `ENCRYPTION_KEY`** في `index.html` (أو `config.js` بعد البناء) لقيمة سرية عشوائية طويلة، واحتفظ بنسخة منها في مكان آمن منفصل — فقدان المفتاح يعني فقدان القدرة على قراءة أي بيانات مشفّرة (بما فيها الكميات والأسعار) نهائيًا.
3. تأكد إن أول مستخدم Admin مسجّل قبل ما تدّي وصول لباقي الفريق.

## تحديث كبير: تشفير الكميات والأسعار (Full Financial Encryption)

بعد التسليم الأول، تم اتخاذ قرار صريح بتوسيع التشفير ليشمل **كل قيمة مالية وكمية** في النظام (quantity, unit_price, amount, printed_qty, delivered_qty) — مش بس النصوص الحساسة. القرار ده له أثر معماري كبير موضّح بالكامل هنا:

### 1. لماذا هذا تغيير جوهري
قاعدة البيانات (Postgres) **لا يمكنها قراءة نص مشفّر كرقم**. فمستحيل عليها بعد كده تعمل `SUM`، `>`, `<`, أو أي مقارنة رقمية على هذه الأعمدة. وده أثّر على جزئين أساسيين كانا مبنيين بالكامل داخل قاعدة البيانات:

**أ) الحماية من تجاوز الكميات (Guardrails):** كانت 4 Triggers جوه Postgres بتمنع تسجيل كمية أكبر من المتاح (في التخصيص للـ SO، الشحن، الفوترة، الإنتاج). تم **حذفها بالكامل** من `schema.sql` (قسم "QUANTITY GUARDRAILS — MOVED CLIENT-SIDE") ونقل نفس المنطق حرفيًا إلى `src/lib/guardrails.ts`، يعمل الآن في المتصفح قبل أي عملية إضافة. **الأثر الأمني:** هذه الحماية كانت مستحيلة الالتفاف عليها (تعمل حتى لو استُخدم الـ API مباشرة من برا التطبيق)، وبقت الآن **قابلة للالتفاف عليها نظريًا** من مستخدم تقني يتجاوز واجهة التطبيق. هذا تنازل واعٍ ومقصود تمت مناقشته بالتفصيل قبل التنفيذ.

**ب) كل حساب مالي (Totals & Reports):** أكثر من 15 View كانت بتحسب `SUM` مباشرة (قيمة الفرصة، إجمالي الفاتورة، المحصّل، المتبقي، التقارير التحليلية بالكامل). تم **حذفها من `schema.sql`**، وإعادة بناء نفس الحسابات بالضبط كـ JavaScript في `src/lib/aggregates.ts` — يجيب الصفوف الخام (مشفّرة) عن طريق `secureFrom()` (اللي بيفك التشفير تلقائيًا)، ثم يحسب المجاميع في المتصفح.

### 2. طبقة الوصول للبيانات (Data Access Layer) — تلبية لطلب صريح
بدل ما يتكرر نفس منطق فك التشفير والحساب في كل صفحة، تم بناء:
- **`src/lib/repository/queries.ts`** — كل عمليات القراءة تمر من هنا (بديل الـ Views المحذوفة).
- **`src/lib/repository/mutations.ts`** — كل عمليات الكتابة تمر من هنا، وهو المكان الوحيد اللي بيستدعي فحوصات `guardrails.ts` تلقائيًا قبل أي إضافة كمية جديدة.

أي صفحة جديدة في المستقبل **لازم تستخدم هذين الملفين** بدل النداء المباشر على `supabase`/`secureFrom` للجداول اللي فيها كميات/أسعار — وإلا فحص الحماية ممكن يتفوت بالغلط.

### 3. الأداء
كل الحسابات (البحث، الفلترة، الفرز، المجاميع) بقت بتحصل بجلب البيانات كاملة (غير مرشّحة) وفك تشفيرها والحساب عليها في المتصفح، بدل ما تحصل في قاعدة البيانات مباشرة. مقبول تمامًا لحجم بيانات متوسط (آلاف السجلات)، لكن هيبقى أبطأ تدريجيًا مع نمو البيانات جدًا (عشرات الآلاف+) — لو حصل ده، الحل هو الانتقال لتشفير عبر Supabase Edge Function (تم شرحه في المحادثة الأصلية) بدل التشفير في المتصفح، عشان الحساب يرجع يحصل في السيرفر.

## تحديث: شاشة التحصيلات (Collections) بدل Payments

- شاشة **Payments** القديمة (عرض فقط) اتشالت، ومكانها شاشة **`/collections`** جديدة فيها:
  1. **عرض كل التحصيلات المسجّلة** (نفس وظيفة الشاشة القديمة).
  2. **زرار "+ تسجيل تحصيل"**: تسجيل تحصيل يدوي على أي فاتورة عليها رصيد متبقي مباشرة من الشاشة دي (مش لازم تدخل تفاصيل الفاتورة الأول).
  3. **زرار "⬆ استيراد تقرير أعمار العملاء"**: استيراد ملف Excel شهري لتقرير أعمار العملاء (SAP)، بالأعمدة: `SAP Code, Invoice No., Invoice Date, Invoice Balance, Credit Term, Aging Report Date, Days`.

### آلية استنتاج التحصيلات من تقرير الأعمار
1. المستخدم يدخل **تاريخ التقرير (As of Date)** ويرفع الملف.
2. النظام يجيب كل الفواتير في التطبيق **بتاريخ قبل تاريخ التقرير ده** وبحالة غير ملغاة/مسودة/محصّلة بالفعل.
3. أي فاتورة من دول **رقمها مش موجود في عمود "Invoice No." بالملف** → يُفترض إنها اتحصّلت بالكامل (لأن SAP كان هيسردها لو لسه عليها رصيد).
4. تظهر قائمة معاينة (Preview) قبل أي حفظ فعلي — المستخدم يقدر يشيل أي فاتورة من القائمة قبل الاعتماد.
5. عند الاعتماد: يتسجّل **تحصيل واحد بالضبط بقيمة الرصيد المتبقي الحالي** لكل فاتورة (مش قيمة تقديرية)، بتاريخ = تاريخ التقرير، وبملاحظة صريحة "مُستنتج تلقائيًا من تقرير أعمار العملاء" — عشان تكون مميّزة بوضوح عن أي تحصيل مُدخل يدويًا، وحالة الفاتورة تتحدّث لـ "مدفوعة بالكامل".

**ملاحظة على مطابقة الأعمدة:** الكود متسامح مع اختلافات بسيطة في حالة الأحرف والمسافات في أسماء الأعمدة (`Invoice No.` أو `invoice no` أو `Invoice Number` كلها هتتعرف تلقائيًا) — لو الملف اتغيّر شكله جوهريًا مستقبلاً، هيظهر رسالة خطأ واضحة تحدد الأعمدة الناقصة بدل ما يفشل بصمت.

## تحديث: موديول أسعار الصرف (FX Rates) وتوحيد كل الأرقام بالدولار

### الفكرة
معظم الأرقام في النظام بالدولار، لكن بعض المستندات ممكن تتسجّل بعملة تانية (جنيه، يورو...). أي مكان في التطبيق بيجمع مبالغ من مستندات متعددة (الداشبورد، التقارير، إجمالي أي قائمة) كان بيجمعها **كأرقام خام بدون تحويل** — وده كان Bug موجود بالفعل (جمع 100 دولار + 100 جنيه = "200" بلا معنى). تم حل المشكلة دي بالكامل.

### آلية التحويل
- **View: أسعار صرف شهرية لكل عملة** — الأدمن يدخل يدويًا: "كام وحدة من العملة دي = 1 دولار" لكل شهر، من شاشة **`/fx-rates`** الجديدة.
- **قاعدة التحويل**: `القيمة بالدولار = القيمة بالعملة ÷ سعر صرف (عملة المستند + شهر تاريخ المستند نفسه)` — مش سعر اليوم الحالي، عشان الأرقام التاريخية تفضل ثابتة.
- **لو الشهر بالظبط مفيش له سعر مسجّل**: يستخدم أقرب شهر **أسبق** ليه سعر مسجّل لنفس العملة (Fallback تلقائي).
- **تنبيه استباقي**: شاشة `/fx-rates` بتفحص كل المستندات الفعلية في النظام وتوريك أي عملة/شهر مستخدم فعليًا وملوش سعر صرف مسجّل خالص — مع زرار سريع لإضافته على طول.

### الأماكن اللي اتصلحت
كل الأماكن دي بقت بتحوّل لدولار (حسب عملة وتاريخ كل مستند) قبل الجمع، بدل ما تجمع أرقام خام:
- الداشبورد: المبالغ المستحقة + جدول الإيرادات حسب المنطقة.
- التقارير: الإيرادات حسب المنطقة/العميل، أداء المنتجات، الإيرادات الشهرية.
- **الإجمالي (Grand Total)** أسفل قوائم Opportunities / Quotations / Invoices.
- شاشة استيراد تقرير أعمار العملاء (إجمالي المبالغ المُستنتج تحصيلها).
- التقرير الهرمي: كل مستوى (فرصة/عرض/أمر بيع/فاتورة) بيعرض دلوقتي **عملته الحقيقية** بدل ما يفترض عملة افتراضية غلط.

### ملاحظة مهمة
جدول `fx_rates` **غير مشفّر عمدًا** (أسعار الصرف مش بيانات حساسة، وبتتقرأ بكثرة في كل تقرير فمفيش داعي نكرر مشكلة التشفير هنا لصفر فايدة خصوصية).

## تحديث: شاشة التحصيلات (Collections) بدل Payments

- شاشة **Payments** القديمة (عرض فقط) اتشالت، ومكانها شاشة **`/collections`** جديدة فيها:
  1. **عرض كل التحصيلات المسجّلة** (نفس وظيفة الشاشة القديمة).
  2. **زرار "+ تسجيل تحصيل"**: تسجيل تحصيل يدوي على أي فاتورة عليها رصيد متبقي مباشرة من الشاشة دي.
  3. **زرار "⬆ استيراد تقرير أعمار العملاء"**: استيراد ملف Excel شهري لتقرير أعمار العملاء (SAP)، بالأعمدة: `SAP Code, Invoice No., Invoice Date, Invoice Balance, Credit Term, Aging Report Date, Days`.

### آلية استنتاج التحصيلات من تقرير الأعمار
1. المستخدم يدخل **تاريخ التقرير (As of Date)** ويرفع الملف.
2. النظام يجيب كل الفواتير في التطبيق بتاريخ قبل تاريخ التقرير ده وبحالة غير ملغاة/مسودة/محصّلة بالفعل.
3. أي فاتورة من دول رقمها مش موجود في عمود "Invoice No." بالملف → يُفترض إنها اتحصّلت بالكامل.
4. تظهر قائمة معاينة (Preview) قبل أي حفظ فعلي.
5. عند الاعتماد: يتسجّل تحصيل واحد بقيمة الرصيد المتبقي الحالي لكل فاتورة، بملاحظة صريحة "مُستنتج تلقائيًا"، وحالة الفاتورة تتحدّث لـ "مدفوعة بالكامل".

## تحديث: جلب أسعار الصرف تلقائيًا (Auto-fetch)

بدل إدخال سعر الصرف يدويًا كل مرة، شاشة **`/fx-rates`** بقى فيها:

- **زرار 🔄 بجنب كل شهر ناقص**: بيجيب سعر آخر يوم في الشهر ده تلقائيًا، ويعرضه في الفورم **للمراجعة والتأكيد** قبل الحفظ (مش حفظ تلقائي صامت).
- **3 مصادر مستقلة تمامًا عن بعض بالترتيب** (لو الأول فشل بالكامل — انقطع أو اتقفل — يجرّب التاني تلقائيًا، وهكذا):
  1. `fawazahmed0/currency-api` (عبر jsDelivr CDN، وله مرآة احتياطية `pages.dev` داخليًا) — +150 عملة.
  2. `Frankfurter` (api.frankfurter.dev) — بيانات بنوك مركزية، 201 عملة.
  3. `exchangerate.host` — مصدر مستقل تاني، ~170 عملة.
  
  الشاشة بتوريك أي مصدر فعليًا اتستخدم لكل سعر (زي "تم الجلب بتاريخ 2026-06-30 (Frankfurter (ECB))") — شفافية كاملة.
- **زرار "🔄 جلب تلقائي للكل"**: بيجيب ويحفظ كل الأشهر الناقصة دفعة واحدة من غير مراجعة فردية — مناسب لو واثق في المصدر وعايز سرعة.
- بيشتغل بالكامل من متصفح المستخدم (Client-side fetch مباشر) — **مفيش حاجة تتنصّب أو تتنشر** إضافي، شغّال فورًا.

### الفرق بين ده وبين "أتمتة كاملة بدون تدخل بشري"
الحل ده يشتغل بس لما حد **يفتح شاشة `/fx-rates` ويدوس الزرار**. لو عايز الأسعار تتحدّث لوحدها شهريًا حتى لو محدش فتح التطبيق خالص، الخطوة الجاية هي **Supabase Edge Function مجدولة شهريًا (pg_cron)** بتنادي نفس الـ API وتحفظ في `fx_rates` مباشرة — ده محتاج نشر (`supabase functions deploy`) من جانبك عن طريق Supabase CLI، لأنه خارج نطاق التنفيذ المباشر المتاح هنا. لو حابب تتوسع للحل ده مستقبلًا، قولّي وهجهزلك كود الـ Edge Function.

**ملاحظة على الدقة:** المصدر ده بيانات تاريخية موثوقة (snapshots يومية محفوظة)، لكنه مش نفس دقة نشرات البنك المركزي الرسمية. لو محتاج دقة محاسبية رسمية (مطابقة تمامًا لسعر البنك المركزي المصري مثلاً)، فضّل الإدخال اليدوي من نشرة البنك، واستخدم الجلب التلقائي كنقطة بداية سريعة تراجعها بس.
